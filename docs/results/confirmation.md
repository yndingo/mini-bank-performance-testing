# Подтверждающий тест

## Цель

Проверить, способна ли текущая конфигурация стенда длительно
поддерживать рабочую интенсивность около 1000 HTTP-запросов/с,
выбранную по результатам поиска производительности.

Проверяются:

- сохранение целевого HTTP RPS;
- ошибки;
- динамика клиентских задержек;
- потребление ресурсов приложения и БД;
- отсутствие устойчивой деградации к концу теста.

Основание выбора интенсивности:
[поиск производительности](capacity-search.md).

## Идентификация запуска

- Дата: 08.11.2026.
- Часовой пояс графиков: UTC+5.
- Сценарий: `mini-bank-read`.
- RunId: `monitoring-check-12`.

На скриншоте JMeter выбран временной диапазон
18:08:50–19:14:41.

Этот диапазон является диапазоном отображения Grafana,
а не точным временем начала и окончания плато.

## Стенд и сценарий

Ресурсные ограничения сохранены относительно поиска:

- приложение: 1 CPU и 1 GiB памяти;
- PostgreSQL: 1 CPU и 1 GiB памяти;
- JVM приложения: `-Xms256m -Xmx512m`.

Сценарий состоит из двух последовательных GET:

1. `GET /api/accounts`.
2. Извлечение accountId.
3. `GET /api/accounts/${accountId}/operations`.

Используется заранее полученный токен одного клиента.
Доступ к приложению выполняется через SSH-туннель.

Регистрация, авторизация, переводы и платежи
в нагрузочный профиль не входят.

## Профиль нагрузки

Ultimate Thread Group:

| Параметр | Значение |
|---|---:|
| Потоки | 200 |
| Начальная задержка | 0 с |
| Разгон | 300 с |
| Удержание | 3600 с |
| Завершение потоков | 0 с |

Профиль UTG:

```text
200 / 0 / 300 / 3600 / 0
```

Плановая длительность:

- разгон — 5 минут;
- плато — 60 минут;
- весь профиль — 65 минут.

Constant Throughput Timer:

- 300 samples/min на поток;
- режим `This thread only`.

Целевая суммарная интенсивность — 1000 HTTP RPS.
Ожидаемое распределение при двух GET в каждой итерации —
примерно по 500 HTTP RPS на каждый запрос.

## Метод оценки

Для оценки использованы графики:

- JMeter: потоки, RPS, ошибки, клиентский p95, scrape status;
- приложение: серверная частота запросов, среднее время, HTTP-ошибки;
- cAdvisor: CPU, working set и CPU-троттлинг;
- PostgreSQL: сессии, транзакции и блокировки.

Основные выводы относятся к плато после разгона.
Падение RPS на правой границе графика рассматривается
отдельно от установившейся нагрузки как участок завершения теста.

Численные значения ниже приблизительные, считаны с графиков.
Точные итоговые агрегаты за плато в этом отчёте не рассчитывались.

Диапазон значений графика p95 не является единым
p95 всех запросов за час.

## Результаты по нагрузке и ошибкам

| Показатель | Наблюдение |
|---|---|
| Активные потоки на плато | 200 |
| GET accounts | Около 500 HTTP RPS |
| GET operations | Около 500 HTTP RPS |
| Суммарная интенсивность | Около 1000 HTTP RPS |
| Ошибки запросов JMeter | На графике не наблюдались |
| Серверные HTTP 4xx/5xx под нагрузкой | На графике не наблюдались |

Линии двух GET почти совпадают.
Значение около 500 RPS на панели отдельных запросов
не является суммарным RPS всего сценария.

Клиентские и серверные графики согласуются:
целевая интенсивность сохранялась на плато.

На основной части интервала scrape status JMeter равен 1.
Это подтверждает доступность endpoint метрик на отображаемом
интервале, но само по себе не заменяет проверку успешности запросов.

## Клиентские задержки

Клиентский p95 не был постоянным:

- значительную часть плато находился примерно в диапазоне 50–90 мс;
- около 18:35–18:43 повышался, достигая примерно 160–165 мс;
- около 18:43–18:46 снизился примерно до 50 мс;
- затем снова вырос;
- к концу плато составлял примерно 70–80 мс.

При изменении задержек интенсивность оставалась около целевой.

Устойчивого ухудшения задержек к концу теста не выявлено.
При этом утверждать, что время ответа было неизменным
на протяжении всего часа, нельзя.

Показатели серверного среднего времени ответа
не подменяют клиентский p95: это разные показатели
с разной точкой измерения.

## CPU и память

| Показатель | Приблизительное наблюдение на плато |
|---|---|
| CPU приложения | 0,83–0,88 CPU |
| CPU PostgreSQL | 0,39–0,42 CPU |
| Working set приложения | Немного выше 512 MiB, после начального роста стабилен |
| Working set PostgreSQL | Без заметного непрерывного роста |

Заметного непрерывного роста working set приложения
в течение теста не наблюдалось.

Это наблюдение ограничено длительностью теста
и не является доказательством отсутствия утечек памяти вообще.

## CPU-троттлинг

У приложения наблюдался существенный CPU-троттлинг.

Доля периодов с троттлингом на большей части плато
составляла приблизительно 45–60%, с временным снижением.

Около 18:44, близко к моменту снижения клиентского p95,
отображаемое время троттлинга уменьшилось приблизительно
с 0,6–0,7 до 0,15 с/с.

Среднее потребление CPU приложения при этом
не уменьшилось в несколько раз.

Совпадение изменений во времени является наблюдением,
но не доказывает причинно-следственную связь.

Доля периодов с троттлингом не равна доле потерянной
производительности приложения.

Поэтому результат не описывается как работа
с большим свободным запасом CPU.

## Наблюдения по PostgreSQL

Наблюдались изменения состояний сессий,
включая отдельные всплески idle in transaction,
и числа блокировок AccessShare.

Эти показатели сами по себе не доказывают,
что запросы ожидали блокировок.

По представленным панелям PostgreSQL
не установлен как доказанное узкое место системы.

Панели объёмов Fetch/Return/Insert/Update/Delete
не используются для численного вывода о скорости обработки:
для этого требуется отдельно проверить PromQL
и преобразование единиц.

## Изменение режима обработки

Как и в поисковом тесте, на подтверждении наблюдалось
снижение задержек при сохранении интенсивности.

В подтверждающем прогоне рядом с этим изменением
также уменьшилось время CPU-троттлинга.

По используемым графикам времени старта контейнеров
признаков перезапуска приложения и БД не обнаружено.

Причина изменения режима не установлена.
Прогрев JVM, кэширование или особенности SQL
не объявляются доказанным объяснением.

Диагностика двухсекундных срезов JTL из поискового прогона
не переносится автоматически на подтверждающий прогон.

## Итог

В пределах выполненного теста подтверждена способность
текущего стенда поддерживать около 1000 суммарных HTTP RPS
на часовом плато сценария чтения двух GET.

По графикам ошибки под нагрузкой не наблюдались.
Устойчивой деградации задержек к концу плато не выявлено.

Задержки внутри плато менялись.
Приложение работало с существенным CPU-троттлингом.

1000 HTTP RPS принято как подтверждённая рабочая точка
среди проверенных режимов, а не абсолютный максимум системы.

## Ограничения вывода

- Один клиентский контекст авторизации.
- Подготовленные тестовые данные.
- Только чтение счетов и истории операций.
- Доступ через SSH-туннель.
- Фиксированные ресурсные ограничения.
- Длительность плато — один час.
- Численные оценки получены по графикам.
- Критерии SLA отдельно не заданы.

Результат не является оценкой производительности регистрации,
авторизации, переводов и платежей и не переносится автоматически
на множество разных клиентов.
