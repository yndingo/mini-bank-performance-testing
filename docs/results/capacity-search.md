# Поиск производительности

## Цель

Проверить поведение приложения при ступенчатом увеличении нагрузки
и выбрать рабочую интенсивность для подтверждающего теста.

В рамках задания этот прогон используется как поиск максимальной
производительности. При этом абсолютный предел системы с точностью
до конкретного RPS не определяется: сравниваются три выбранные ступени.

## Стенд и ограничения

- Приложение: Java Spring Boot.
- База данных: PostgreSQL.
- Развёртывание: Docker Compose на Ubuntu.
- Лимит приложения: 1 CPU и 1 GiB памяти.
- Лимит PostgreSQL: 1 CPU и 1 GiB памяти.
- JVM приложения: `-Xms256m -Xmx512m`.
- Генератор нагрузки: JMeter 5.4.1 на отдельном клиентском ПК.
- Доступ к приложению: через SSH-туннель.
- Во время теста ресурсные ограничения не изменялись.

Конфигурация сервисов приведена в [compose.yaml](../../compose.yaml).

## Сценарий

Каждая итерация включает два последовательных HTTP-запроса:

1. `GET /api/accounts`.
2. Извлечение `accountId` из ответа.
3. `GET /api/accounts/${accountId}/operations`.

Используется заранее полученный Bearer-токен одного клиента.

Потоки JMeter не представляют разных зарегистрированных клиентов.
Регистрация, авторизация, переводы и платежи в нагрузочный профиль
этого теста не входят.

## Настройки генератора

- Ultimate Thread Group.
- Constant Throughput Timer: 300 samples/min на поток.
- Режим таймера: `This thread only`.
- HTTP implementation: `HttpClient4`.
- KeepAlive включён.
- View Results Tree выключен.
- Метрики JMeter передаются в Prometheus.

Таймер задаёт целевую частоту HTTP-сэмплов, а не итераций сценария.

300 samples/min соответствует 5 HTTP-запросам/с на поток.
Поскольку в итерации два GET, целевая суммарная интенсивность
при 200 потоках составляет 1000 HTTP RPS, а не 2000.

Transaction Controller `test` не считается дополнительным
HTTP-запросом и не прибавляется к HTTP RPS.

## Профиль нагрузки

| Ступень | Потоки | Разгон до ступени | Плато | Целевой суммарный HTTP RPS |
|---|---:|---:|---:|---:|
| 1 | 150 | 5 минут | 20 минут | 750 |
| 2 | 200 | 5 минут | 20 минут | 1000 |
| 3 | 250 | 5 минут | 20 минут | 1250 |

Общая продолжительность по профилю — 75 минут.

При переходе между ступенями добавляются потоки:
150 → 200 → 250.

Разгоны и переходные участки не используются как характеристика
установившегося режима.

## Наблюдаемые метрики

- HTTP RPS отдельно для каждого GET.
- Ошибки HTTP-запросов и проверок JMeter.
- Клиентский p95 и его изменение во времени.
- CPU и working set контейнеров приложения и БД.
- Доля периодов с CPU-троттлингом и время троттлинга.
- Состояния сессий, транзакции и блокировки PostgreSQL.

Значения, считанные с графиков, являются приблизительными.
Диапазон значений временного ряда p95 не является единым
p95 всех запросов за плато.

## Диагностические и прерванные попытки

До итогового сравнения были обнаружены проблемы,
которые не следует считать пределом производительности приложения.

### Накопление клиентских соединений

В одном из ранних прогонов возникали ошибки:

`java.net.BindException: Address already in use: connect`

Одновременно на клиентском ПК росло количество соединений TIME_WAIT.

Для HTTP-запросов были выбраны HttpClient4 и KeepAlive.
В `user.properties` JMeter установлено:

```properties
httpclient.reset_state_on_thread_group_iteration=false
```

После изменения на проверенном участке количество соединений
перестало накапливаться прежним образом.

Загрязнённый ошибками генератора прогон не используется
для определения производительности приложения.

### Истечение токена

Одна из попыток трёхступенчатого теста была прервана
из-за истечения срока действия токена авторизации.

Данные после появления ошибок авторизации исключены
из оценки производительности бизнес-сценария.

Последующее сравнение ступеней относится к повторному прогону,
а не к участку с истёкшим токеном.

## Результаты поиска

Приблизительные значения по графикам:

| Потоки | Целевой суммарный HTTP RPS | Фактический суммарный HTTP RPS на плато | Клиентский p95 |
|---|---:|---:|---|
| 150 | 750 | Около 750 | Примерно 85–95 мс |
| 200 | 1000 | Около 1000 | Сначала примерно 90–150 мс, после изменения режима — около 40–75 мс |
| 250 | 1250 | Преимущественно около 1100–1160 после переходного пика | Примерно 380–440 мс |

На второй ступени целевая интенсивность достигалась.

На третьей ступени увеличение целевой интенсивности на 25%
не обеспечило её устойчивого достижения.
Фактическая интенсивность выросла примерно на 10–16%
относительно второй ступени, при этом задержки существенно выросли.

Следовательно, третья ступень дала сравнительно небольшой прирост
пропускной способности ценой значительного ухудшения времени ответа.

## Изменение режима внутри второй ступени

Около 08.11.2026 16:57 UTC+5 на второй ступени наблюдалось
снижение CPU приложения и клиентских задержек
при сохранении интенсивности запросов.

Для проверки сопоставимости запросов были выделены
два двухсекундных среза JTL:

- до изменения: 16:53:00–16:53:02 UTC+5;
- после изменения: 17:02:00–17:02:02 UTC+5.

### Сравнение срезов JTL

| Показатель | До | После |
|---|---:|---:|
| Accounts: число запросов | 1000 | 1000 |
| Operations: число запросов | 1000 | 1000 |
| Суммарный HTTP RPS | 1000 | 1000 |
| Неуспешные запросы | 0 | 0 |
| Accounts: среднее время | 48,82 мс | 16,09 мс |
| Operations: среднее время | 65,90 мс | 20,85 мс |
| Accounts: размер ответа | 341 байт — 1000 ответов | 341 байт — 1000 ответов |
| Operations: размер ответа | 2993 байта — 980; 2964 байта — 20 | 2993 байта — 976; 2964 байта — 24 |

Во всех запросах этих срезов получены HTTP 200 и success=true.
URL и выбранный accountId совпадали.

Снижение задержек в срезах не сопровождалось снижением частоты
запросов или заметным изменением распределения размеров ответов.

Одинаковый размер ответа не доказывает идентичность содержимого JSON
или одинаковый объём работы внутри приложения и БД.

По использованным метрикам времени старта контейнеров
признаков перезапуска приложения и БД не обнаружено.

Двухсекундные срезы использованы только для диагностики запросов.
Они не характеризуют устойчивые p95/p99 всего плато.

Причина изменения режима не установлена.
Прогрев JVM, кэширование или изменение поведения SQL
не объявляются доказанными причинами.

## Наблюдения по БД

На отдельных участках наблюдались изменения состояний сессий
и всплески числа блокировок.

Само количество блокировок не доказывает ожидание блокировок
или наличие блокировочного узкого места.

По имеющимся данным конкретная причина ограничения
производительности внутри Java или PostgreSQL не установлена.

## Вывод

Среди проверенных режимов выбрана рабочая точка:

- 200 потоков JMeter;
- Constant Throughput Timer 300 samples/min на поток;
- около 1000 суммарных HTTP-запросов/с.

Выбор обусловлен достижением целевой интенсивности на второй ступени
и существенным ростом задержек при переходе к третьей.

1000 HTTP RPS — не абсолютный максимум системы,
а выбранная рабочая точка для последующего подтверждения.
