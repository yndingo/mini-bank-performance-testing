## Цель

Определить поведение текущего сценария чтения при росте нагрузки
без изменения ресурсных ограничений стенда.

## Ограничения

- CPU приложения: 1 CPU.
- Остальные лимиты и настройки фиксируются по Compose.
- Один клиентский контекст авторизации.
- Два последовательных GET-запроса в каждой итерации.
- Доступ к приложению через SSH-туннель.

## Профиль поиска производительности

Constant Throughput Timer: 300 samples/min на поток.
Режим: this thread only.

| Ступень | Потоки | Разгон | Плато | Целевой HTTP RPS |
|---|---:|---:|---:|---:|
| 1 | 150 | 5 минут | 20 минут | 750 |
| 2 | 200 | 5 минут | 20 минут | 1000 |
| 3 | 250 | 5 минут | 20 минут | 1250 |

Общая продолжительность: 75 минут.

## Метрики

- Фактический HTTP RPS.
- Ошибки.
- p95/p99 и динамика задержек.
- CPU и память приложения и PostgreSQL.
- CPU-троттлинг.
- Состояния сессий и ожидания БД.

Статистика оценивается отдельно на каждом плато.
Разгоны не включаются в сравнение установившихся режимов.

# Подтверждающий тест

## Результат

В запуске monitoring-check-12 подтверждена способность текущей
конфигурации стенда поддерживать около 1000 HTTP-запросов/с
для сценария чтения из двух последовательных GET.

При 200 потоках JMeter на плато продолжительностью около часа
каждый GET выполнялся с интенсивностью около 500 запросов/с.
По графикам JMeter и приложения ошибки под нагрузкой
не наблюдались.

## Задержки

Клиентский p95 менялся в течение плато:
преимущественно находился около 50–90 мс,
с временным повышением примерно до 160–165 мс.

После повышения задержки снизились при сохранении RPS.
К концу плато p95 составлял примерно 70–80 мс.
Устойчивой деградации к концу теста не выявлено.

Значения приблизительные, оценены по графикам.
Это диапазон значений временного ряда p95,
а не единый p95 за всё плато.

## Ресурсы

Потребление CPU приложения составляло примерно 0,83–0,88 CPU,
PostgreSQL — около 0,39–0,42 CPU.

Память приложения после начального роста стабилизировалась.
Заметного непрерывного роста working set на интервале теста
не наблюдалось.

Приложение работало с существенным CPU-троттлингом.
Около момента снижения задержек уменьшилось и время троттлинга.
Причина изменения режима обработки не установлена.

## Итог и ограничения

1000 HTTP RPS принято как подтверждённая рабочая точка
среди проверенных режимов для текущего сценария,
тестовых данных и ресурсных ограничений.

Результат не определяет абсолютный максимум системы,
не подтверждает наличие существенного ресурсного запаса
и не является проверкой SLA, поскольку критерии SLA
отдельно не заданы.

Проверка выполнена с одним клиентским контекстом авторизации
и доступом через SSH-туннель. Вывод не переносится автоматически
на другие данные, множество клиентов или сценарии записи.
